Why Poseidon? SHA256 and keccak256 require thousands of arithmetic gates inside a ZK circuit. Poseidon is designed for ZK — it uses field arithmetic over BN254 that maps directly to circuit constraints, making it ~100× more efficient. The light-poseidon crate uses circom-compatible constants so the JS poseidon-lite library and Solidity PoseidonT3.sol all produce identical outputs.
Domain tags: Tag 0 = leaf hash · Tag 1 = inner node · Tag 2 = nullifier. These prevent cross-context collisions — a leaf value can never equal an inner node hash because they use different first inputs.

Poseidon Hash Scheme

// Leaf:    domain tag 0
leaf_hash(badge) = Poseidon([0, badge])

// Inner:   domain tag 1
inner_hash(l,r) = Poseidon([1, l, r])

// Nullifier: domain tag 2
nullifier_hash(badge, period)
  = Poseidon([2, badge, period])

Merkle Path Verification (16 levels)

fn verify_merkle_path(badge, path, indices, root) {
  let mut node = leaf_hash(badge);
  for (sib, dir) in path.zip(indices) {
    node = if dir == 0 {
      inner_hash(&node, sib)  // we're left
    } else {
      inner_hash(sib, &node)  // we're right
    };
  }
  node == root  // must equal on-chain root
}

Why a serializing queue? RISC Zero proof generation uses all CPU cores + 4–8 GB RAM. Running two simultaneously OOMs the machine. The queue (proverClient.ts) ensures only one shieldpass-prove process runs at a time. New jobs wait in queue[]; drainQueue() is called after each job finishes.

On-chain Verification Logic

// 1. No replay
require(!isNullifierUsed[nullifier]);

// 2. Tree root is recent (≤7 days)
require(badges.isRootFresh(ensNode, root));

// 3. Rebuild what the ZK guest committed
digest = sha256(abi.encode(
  root, reportHash, nullifier, periodId, ensNode
));

// 4. Verify STARK proof cryptographically
verifier.verify(seal, imageId, digest);

// 5. Mark nullifier used forever
isNullifierUsed[nullifier] = true;

⬡ Nullifier — Anti-Double-Report

One report per worker per period, with zero identity leakage

flowchart LR BADGE["badge\n(private secret)"] PERIOD["periodId\n= floor(now / 7_776_000)\n≈ one per quarter"] NULL["nullifier\n= Poseidon(2, badge, periodId)"] BADGE & PERIOD --> NULL ONCHAIN["isNullifierUsed[nullifier]\non ReportRegistry"] NULL --> ONCHAIN SAME["Same badge\nDifferent period\n→ Different nullifier\n✓ Can file again"] DIFF["Different badge\nSame period\n→ Different nullifier\n✓ Other workers unaffected"] USED["Same badge\nSame period\n→ Same nullifier\n✗ require() reverts"] NULL --> SAME & DIFF & USED classDef null fill:#1f1500,stroke:#ffa657,color:#ffb966 class BADGE,PERIOD,NULL,ONCHAIN,SAME,DIFF,USED null
Privacy property: The nullifier is published on-chain but reveals nothing about which badge produced it — it's just a Poseidon hash. Two nullifiers from the same worker in different periods are completely unlinkable. An observer can confirm "some badge holder filed in Q1" but cannot determine which badge, link it to another period, or count how many workers have filed.
